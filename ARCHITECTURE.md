# ARCHITECTURE

Описание устройства проекта для разработчиков и для Claude Code.

## 1. Общая схема

```
                     app
                      |
        +-------------+--------------+
        |             |              |
    feature:*     core:designsystem  (DI-сборка)
        |
  +-----+--------+----------+---------+
  |              |          |         |
core:playback  core:library core:stats core:tags
  |              |          |         |
  +--------------+----+-----+---------+
                      |
                core:database
                      |
                 core:model
```

Правила зависимостей:
- `core:model` ни от чего не зависит, это чистый Kotlin.
- `core:database` зависит только от `core:model`.
- Остальные `core:*` зависят от `core:model` и `core:database`, но не друг от друга, кроме явно разрешённых связей: `core:library` использует интерфейс чтения тегов из `core:tags`, `core:stats` слушает события из `core:playback` через интерфейс. `feature:tag-editor` берёт из `core:tags` только `TagWritePermission` (системный запрос разрешения на запись, раздел 5).
- `feature:*` зависят от `core:*` и `core:designsystem`, но не друг от друга. Навигация между ними собирается в `app`.
- Интерфейсы объявляются в потребляющем модуле или в `core:model`, реализации внедряются через Hilt.

## 2. Данные и источники правды

| Что | Где хранится | Можно пересобрать? |
|---|---|---|
| Теги трека (название, исполнители, альбом, обложка, текст) | Файлы на устройстве | Это и есть источник |
| Кэш для поиска, сортировки, списков | БД (таблицы track, album, artist и связи) | Да, сканированием |
| Алиасы исполнителей, составные имена, оценки, избранное | БД | Нет, попадают в резервную копию |
| События прослушивания | БД | Нет, попадают в резервную копию |
| Настройки интерфейса и воспроизведения | DataStore | Нет, попадают в резервную копию |
| Уменьшенные обложки | Каталог кэша приложения | Да, из файлов |
| Фото исполнителей (уменьшенная копия того, что выбрал пользователь) | Личная папка приложения (`files/artist_photos`), путь в `artist.photo_uri` | Нет, и в резервную копию JSON не входят (решение владельца, задача 0.3.5b) |

Подробная схема БД в `DATABASE.md`.

## 3. Сканирование библиотеки (`core:library`)

1. Приложение запрашивает разрешение на чтение аудио (`READ_MEDIA_AUDIO` на Android 13+, `READ_EXTERNAL_STORAGE` ниже).
2. Запрос в MediaStore получает список аудиофайлов с `date_modified` и размером. Подкасты и аудиокниги в библиотеку не попадают (флаги MediaStore, расширение `.m4b`).
3. Файлы, которых нет в БД, у которых изменился `date_modified` или которые помечены повреждёнными, ставятся в очередь на чтение тегов (`core:tags`). Остальные пропускаются. Файл открывается по `content://` URI только на чтение, теги читаются по дескриптору без копирования (`FileTagLoader`). Вместе с дескриптором передаётся имя файла из MediaStore (`DISPLAY_NAME`): TagLib выбирает формат по расширению, а без имени угадывает его по содержимому и отвергает часть корректных MP3. Теги из файла важнее данных MediaStore; MediaStore даёт только название (имя файла), если в файле его нет, и длительность, если TagLib её не определил. Нечитаемый файл (не поддерживаемый формат, битый заголовок) индексируется по данным MediaStore. Теги читаются до транзакции, чтобы БД не была заблокирована во время чтения файлов.
4. Имена исполнителей проходят конвейер из раздела 4 и превращаются в сущности `Artist`.
5. Результат записывается в БД транзакциями пачками, UI получает обновления через Flow.
6. Файлы, пропавшие из MediaStore, помечаются удалёнными, история прослушиваний сохраняется.

Во время сканирования в памяти держатся `HashMap<нормализованное имя, artistId>` для исполнителей и такая же карта для алиасов. После завершения сканирования карты освобождаются.

### Кэш обложек

- Интерфейс `CoverRepository` (`core:model`, реализация `DefaultCoverRepository` в `core:library`) отдаёт путь к маленькой обложке трека или альбома (обложка первого трека альбома, у которого она есть). Обложка берётся из файла (`has_cover = 1`), уменьшается до 512 px по большей стороне (обложка плеера занимает около 800 px) и хранится как JPEG (качество 85) в `cacheDir/covers`.
- Ключ файла это SHA-1 от `uri`, размера, `date_modified` трека и размера миниатюры (`coverKey`). Попадание в кэш стоит одного запроса в БД, файл не открывается. Изменённый файл (редактор тега, другое приложение) получает новый ключ, поэтому устаревшая обложка не показывается; старый файл вытесняется лимитом. Столбец `album.cover_hash` не используется, миграции нет.
- Лимит 64 МБ (около 1500 обложек). `CoverDiskCache` (без Android, покрыт юнит-тестами) при превышении удаляет файлы, к которым обращались давнее всего; попадание обновляет время изменения файла. Только что записанная обложка не удаляется никогда.
- Промахи выполняются по одному (мьютекс): память остаётся низкой при прокрутке списка новых обложек, а два запроса одной обложки читают файл один раз. Файл записывается через `.part` и переименование.
- В интерфейсе: `CoverImage` в `core:designsystem` берёт картинку у `CoverLoader` из `LocalCoverLoader` (дизайн-система не знает о `core:model`), до загрузки и без обложки показывает `CoverPlaceholder`. Реализация `AppCoverLoader` в `app` декодирует файлы и держит около 16 МБ последних картинок в памяти (ключ это путь файла).

## 4. Разбиение исполнителей (`core:tags`)

Правило намеренно простое.

Вход: значения поля «Исполнитель» из файла (одно или несколько).

1. **Несколько значений в файле** (Vorbis/FLAC, ID3v2.4): берём как есть, без дальнейшего разбиения. Значение «Tyler, The Creator» там остаётся одним именем.
2. **Одна строка с `;`**: режем только по `;`. Запятые внутри частей не трогаем, поэтому `Tyler, The Creator; Kanye West` разбирается правильно без всяких правил.
3. **Одна строка без `;`**: режем по `,`, затем среди получившихся фрагментов ищем подряд идущие, совпадающие с записью таблицы составных имён (`artist_compound`, сравнение по нормализованным значениям, сначала самые длинные), и склеиваем их обратно в одно имя. Пример: `Tyler, The Creator, Kanye West` даёт `Tyler, The Creator` и `Kanye West`.
4. **Другие разделители не используются** (`&`, `/`, `feat.`, `and`, `x`): имена вроде «Simon & Garfunkel» и «AC/DC» остаются целыми. Если такое имя нужно разделить, это делается вручную в редакторе тега.
5. **Нормализация и алиасы**: ключ имени (без регистра, лишних пробелов) сначала проходит через таблицу алиасов, затем находится или создаётся исполнитель.
6. **Результат** пишется в `track_artist` с `position`. Исходные значения тега хранятся в `track.artist_tag_values`, чтобы пересчитывать разбиение без чтения файлов.

### Составные имена (запятая внутри псевдонима)

Это единственное исключение из правила запятой. Хранится в таблице `artist_compound` (см. `DATABASE.md`).

- **Встроенный список** лежит в репозитории файлом `core/tags/src/main/assets/compound_artists.json` (поля: `version`, список записей с `id` и `name`). Допускаются дополнения через pull request. При запуске, если версия списка выше сохранённой, недостающие записи добавляются в БД по `builtin_id`. Существующие строки не перезаписываются, поэтому выбор пользователя сохраняется.
- **Добавление пользователем** («Remember as one artist»): в списке исполнителей включается режим множественного выбора, пользователь отмечает несколько записей (например, «Tyler» и «The Creator») и нажимает кнопку. Приложение показывает диалог, где пользователь задаёт порядок и написание («Tyler, The Creator»). Диалог проверяет, что имя состоит из выбранных частей. Правило сохраняется как пользовательское (`builtin_id` пусто).
- **Ручное удаление**: пользовательское правило удаляется совсем, встроенное отключается (`enabled = 0`), чтобы после обновления приложения оно не вернулось.
- **После добавления, удаления или отключения правила** пересчитываются только затронутые треки (по `artist_tag_values`, без чтения файлов), затем удаляются осиротевшие исполнители, у которых нет треков, фото и алиасов. Перед удалением правила показывается предупреждение, что исполнитель снова разделится.
- Файлы на устройстве при этом не меняются. Правила живут в БД и попадают в резервную копию (только пользовательские и отключённые встроенные).

## 5. Запись тегов (`core:tags`)

Самое хрупкое место проекта. Библиотека тегов: TagLib через JNI (`docs/decisions/005-tag-library.md`). Алгоритм:

1. Запросить у системы разрешение на изменение файла: на Android 11+ через `MediaStore.createWriteRequest`, на Android 10 через `RecoverableSecurityException`, на Android 8-9 нужно разрешение `WRITE_EXTERNAL_STORAGE`.
2. Проверить свободное место в личной папке приложения: нужно около двух размеров файла (рабочая копия и резервная копия).
3. Скопировать исходный файл в рабочую копию в личной папке приложения.
4. Записать теги в рабочую копию. Сначала читается полный набор тегов из файла (`PropertyMap`), в нём меняются только наши поля, и записывается он целиком: так сохраняются неизвестные кадры и поля (`TXXX`, `PRIV`, свои поля Vorbis и т.п.). Для MP3 сохраняется исходная версия ID3 (v2.3 остаётся v2.3, v2.4 остаётся v2.4), её нужно передавать при сохранении явно.
5. Прочитать рабочую копию заново и сверить записанные значения с ожидаемыми. Проверить, что аудиоданные не изменились:
   - MP3 и FLAC: хеш байтов аудио после блока тегов;
   - M4A: хеш содержимого `mdat`;
   - OGG и Opus: сравнение аудиопакетов, а не байтов файла, потому что TagLib может перекладывать страницы;
   - для всех форматов: длительность и частота дискретизации по TagLib совпадают с исходными.
6. Создать резервную копию оригинала в личной папке приложения и записать в журнал, что началась замена.
7. Заменить оригинал: записать содержимое проверенной рабочей копии через дескриптор файла (`openFileDescriptor(uri, "rwt")`). Переименовать копию поверх оригинала под scoped storage нельзя, поэтому замена не атомарна.
8. Перечитать оригинал и сверить с рабочей копией (размер и хеш). Только после этого удалить резервную копию и запись в журнале.
9. При любой ошибке до шага 7 оригинал не тронут. При ошибке на шагах 7-8 оригинал восстанавливается из резервной копии. В обоих случаях пользователю показывается понятное сообщение.
10. При запуске приложения проверяется журнал: если замена не была завершена (процесс убит, телефон выключился), оригинал восстанавливается из резервной копии.

Несколько исполнителей пишутся штатно как отдельные значения для Vorbis/FLAC и ID3v2.4. Для ID3v2.3 используется одна строка с разделителем `; ` (то же правило читается при разборе).

### Запись: как устроено

- Интерфейс `TagWriter` и модели (`TagWriteTarget`, `TagEdit`, `CoverEdit`, `TagWriteResult`) лежат в `core:model`, реализация `SafeTagWriter` в `core:tags`. Записи идут по одной (мьютекс).
- `TagEdit` содержит желаемое состояние наших полей целиком. Поле, равное уже записанному, не переписывается, поэтому сохраняется его форма: полная дата `2024-05-01`, написание `TOTALTRACKS`, несколько текстов. Наложение правки на `PropertyMap` выполняет `PropertyEditor`, тестируется таблицей без нативного кода. Правила: исполнители, исполнители альбома и жанры в ID3v2.3 склеиваются через `; `; в ID3v2 и MP4 номер и итог хранятся вместе (`3/10`), итог без номера отбрасывается; в Vorbis итог идёт в `TRACKTOTAL` (или в `TOTALTRACKS`, если файл уже так пишет); год заменяет всю дату; текст пишется в тот ключ, из которого читался, а удаление текста убирает все ключи с текстами.
- Обложка: `Replace` меняет переднюю обложку (или первую картинку), остальные картинки остаются; `Remove` убирает все картинки, чтобы вместо обложки не всплыла другая.
- MP3 сохраняется с исходной версией ID3v2, файл без ID3v2 получает v2.4 (параметр `id3v2VersionForNewTags`, настройка появится в 0.5.1). ID3v1 пишется, только если он уже был: TagLib держит пустой ID3v1 для каждого MPEG-файла и иначе дописал бы его. Поддержка APE в TagLib не собрана, тег APEv2 остаётся нетронутыми байтами.
- Нативная запись (`nativeWriteTags`) открывает только рабочую копию по пути и идёт под `NativeCallGuard` с ключом оригинала: файл, уронивший TagLib, уходит в карантин.
- Сверка рабочей копии: `PropertyMap` после записи должен совпасть с записанным целиком, число картинок с ожидаемым, новая обложка с переданной. Отпечаток аудио (`AudioFingerprint`) считается на Kotlin, независимо от TagLib: MP3 без ID3v2 в начале и APEv2/ID3v1 в конце, FLAC после блоков метаданных, содержимое `mdat` у M4A, аудиопакеты с granule position у Ogg Vorbis и Opus (без заголовочных пакетов). Длительность и частота дискретизации по TagLib тоже должны совпасть.
- Доступ к оригиналу идёт через `OriginalFiles`: `MediaStoreOriginalFiles` для `content://` (проверка права открытием на `"rw"` без обрезки, замена через `"rwt"` с явной обрезкой и `sync()`), `PathOriginalFiles` для путей и JVM-тестов. Резервная копия снимается после сверки и сравнивается по SHA-256 с тем, что было скопировано в рабочую копию: если файл успел поменяться, запись отменяется (`FileChanged`).
- Журнал (`WriteJournal`) лежит в `noBackupFilesDir/tag-write`: папка на каждую запись с рабочей копией, резервной копией и файлом `journal.properties` (цель, SHA-256 старого и нового содержимого). Файл журнала существует ровно между созданием резервной копии и успешной сверкой оригинала; пишется через временный файл, `sync()` и переименование. Папка без журнала считается остатком и удаляется.
- Восстановление (`TagFileRecovery`) выполняется один раз за процесс перед первым чтением или записью тегов, вместе с переносом аварийных меток в карантин. Если оригинал совпадает со старым или новым содержимым, папка удаляется, иначе оригинал восстанавливается из резервной копии. Если восстановить не удалось (например, на Android 11+ пропало разрешение на запись), папка остаётся: восстановление повторится при следующем запуске и перед следующей записью в этот же файл, а сама запись до этого не начнётся.
- Разрешение: `TagWritePermission` строит запрос для экрана: системный диалог `createWriteRequest` на Android 11+, `RecoverableSecurityException` на Android 10, `WRITE_EXTERNAL_STORAGE` (в манифесте `core:tags` с `maxSdkVersion=28`) на Android 8–9. Показывает его редактор тегов (0.3.6), когда запись вернула `NeedsPermission`.
- Тесты: `SafeTagWriterTest` на хостовой сборке проходит все эталоны, включая `extra_*` с неизвестными полями (TXXX, PRIV, APEv2, ID3v1, свои поля Vorbis, freeform MP4), и подставляет сбои: ошибка посреди замены, гибель процесса посреди замены и сразу после неё, изменение файла во время записи, порча аудио в рабочей копии. `SafeTagWriterDeviceTest` (инструментальный) заменяет настоящий файл MediaStore через `content://` и проверяет, что после замены приложение остаётся владельцем файла (`owner_package_name`) и файл не в состоянии `is_pending`: запись через `"rwt"` строку MediaStore не пересоздаёт, владельца не меняет. В задаче 0.3.3 он прошёл на телефоне с Android 16. Однажды на этом телефоне тест упал при удалении файла в `tearDown` (`SecurityException`), повторить сбой не удалось; теперь очистка не роняет тест, а пишет в лог владельца и `is_pending`.

### Чтение и JNI

- Перед нативным чтением файл помечается меткой «в обработке», после успешного чтения метка снимается. Если процесс упал в нативном коде, при следующем запуске файл с меткой пропускается и помечается в БД как повреждённый, сканирование продолжается со следующего.
- Строки между Kotlin и C++ передаются как байты UTF-8 в обе стороны (не через `NewStringUTF`, который ломает символы вне BMP). Тест на эмодзи в тегах обязателен.
- Замер скорости чтения на реальном телефоне с большой библиотекой является условием закрытия задачи на чтение тегов.
- Каждый нативный вызов с пользовательским файлом оборачивается в `NativeCallGuard.runGuarded` (`core:tags`): метка лежит файлом в личной папке, по одному на вызов. При запуске `recoverAfterCrash()` переносит оставшиеся метки в карантин, `isQuarantined()` пропускает такие файлы. При параллельном чтении в карантин попадают все файлы, читавшиеся в момент падения. `recoverAfterCrash()` вызывается один раз перед первым чтением или записью процесса (`TagFileRecovery`). Файл в карантине возвращает `TagReadResult.Quarantined`, сканер записывает его по данным MediaStore с `track.is_damaged = 1` и пробует снова при каждом сканировании (пока файл в карантине, это одна проверка по списку).
- Чтение по дескриптору идёт через `dup()`: дескриптор вызывающего остаётся открытым, но смещение в файле у копии общее и сдвигается.
- Интерфейс `TagReader` и модели (`TrackTags`, `FileTags`, `AudioInfo`, `EmbeddedPicture`) лежат в `core:model`, реализация `TagLibTagReader` в `core:tags`. Один нативный вызов отдаёт весь `PropertyMap`, свойства аудио, формат, версию ID3v2 и число картинок; обложка читается отдельным вызовом только по запросу. Разбор `PropertyMap` (номера `3/10` и `TRACKTOTAL`, год из даты, текст из `LYRICS`, `LYRICS:<описание>`, `UNSYNCEDLYRICS`) живёт в `PropertyMapper` и тестируется без нативного кода.
- Исполнители отдаются сырыми значениями тега; разбиение по разделу 4 появится в задаче 0.4.1. Текст песни отдаётся как записан (обычный или LRC), разбор синхронизированных текстов запланирован в версии 1.5.
- Обложка: передняя обложка (тип 3), а если её нет, первая картинка. У MP4 типов картинок нет, обложка считается передней.
- TagLib выбирает формат по расширению и открывает «MP3» без единого MPEG-кадра; мост считает такой файл нечитаемым.
- Эталонные файлы и скрипт их генерации (mutagen, независимый от TagLib) лежат в `core/tags/src/test/`. Фаззинг-тест читает обрезанные и испорченные копии эталонов, созданные из фиксированного зерна.
- Замер на телефоне: `TagReadBenchmark` (инструментальный тест `core:tags`) читает всю библиотеку устройства так же, как сканер. Результаты задачи 0.3.2 записаны в `docs/decisions/005-tag-library.md` (риск 5): около 6,5 мс на файл при тёплом кэше, основное время уходит на ввод-вывод через FUSE.

### Сборка нативной части

- Исходники TagLib подключены git submodule `core/tags/src/main/cpp/taglib`, закреплены на теге `v2.3.2` (вместе с вложенным utfcpp). После клонирования: `git submodule update --init --recursive`. Обновление версии: checkout нового тега в submodule, коммит gitlink, проверка тестов `core:tags`.
- Версии NDK и CMake зафиксированы в `gradle/libs.versions.toml` (`ndk`, `cmake`) и продублированы в `.github/workflows/ci.yml`. Оба пакета ставятся через `sdkmanager`.
- Android: `externalNativeBuild` собирает `libtaglib_jni.so` для arm64-v8a, armeabi-v7a, x86_64 (`c++_static`, в release `MinSizeRel`).
- JVM-тесты: задача `buildHostTagLib` собирает тот же CMake-проект под хост CMake'ом из SDK и системным компилятором C++ (Xcode Command Line Tools или gcc/clang), `jni.h` берётся из JDK, на котором запущен Gradle. Если линкер Command Line Tools старее новейшего macOS SDK (ошибка `tapi error: unknown architecture`), в `local.properties` указывается подходящий SDK: `tags.host.osxSysroot=/Library/Developer/CommandLineTools/SDKs/MacOSX26.5.sdk`, либо обновляются Command Line Tools.
- Лицензии: TagLib используется под LGPL-2.1, utfcpp под Boost 1.0 (`docs/decisions/005-tag-library.md`); тексты лицензий лежат в submodule и попадут в экран лицензий приложения.

## 6. Воспроизведение (`core:playback`)

- `MediaSessionService` на Media3 владеет плеером, очередью и `MediaSession`. Приложение подключается к нему через `MediaController`.
- Уведомление, управление с экрана блокировки и кнопками наушников приходят из Media3.
- Очередь и позиция сохраняются в БД или DataStore при изменениях и восстанавливаются при запуске.
- Аудиофокус и отключение наушников обрабатываются штатными механизмами Media3.
- Gapless, ReplayGain и crossfade добавляются в версии 0.5 поверх этого же слоя без смены архитектуры. Их параметры читаются из репозитория настроек (раздел 9) и применяются к плееру в сервисе, а не в UI.

## 7. Статистика (`core:stats`)

- Слушатель плеера пишет `listen_event` при завершении трека или пропуске. Хранится время начала, фактически проигранное время, длительность трека и снимок названия и исполнителей.
- Прослушивание засчитывается, если проиграно не меньше порога (по умолчанию 50% или 4 минуты, настраивается). Пропуски помечаются отдельно.
- Агрегации (топы, карты активности, серии дней) считаются SQL-запросами и Flow, без хранения готовых итогов.
- Исполнители считаются по отдельности через `track_artist`, поэтому "A & B" не появляется отдельной строкой.
- Экспорт и импорт: JSON (полный) и CSV (события). Формат версионируется полем `schemaVersion`.

## 8. Резервная копия

Один файл JSON: алиасы, пользовательские составные имена и отключённые встроенные, события прослушивания, оценки, избранное, настройки. Теги в копию не входят, они находятся в файлах. Импорт проверяет `schemaVersion` и объединяет данные без дублей.

## 9. Интерфейс

- Один `Activity`, навигация Compose Navigation, состояние экранов в ViewModel (`StateFlow`).
- Дизайн-система в `core:designsystem` (цвета, типографика, базовые компоненты), значения берутся из макета Figma. Модуль зависит только от Compose и не зависит от `core:model`: компоненты принимают строки и простые значения, а не `Track`. Список компонентов и образцов в `DESIGN.md`, раздел 5; правила для экранов без макета там же, раздел 7.
- Акцент читается только из `LocalAccent` (`MuzzzloTheme.accent`), константы цветов в экранах запрещены. Остальные токены: `MuzzzloTheme.colors`, `MuzzzloTheme.dimens`, `MaterialTheme.typography`.
- Меню трека: компонент `TrackActionsMenu` отдаёт выбранный пункт как `TrackAction` (enum в `core:designsystem`). Каждая ViewModel, у которой есть строки треков, обрабатывает его в `onTrackAction(track, action)`. Переходы на другие экраны (например, Open queue) ViewModel не выполняет: экран получает колбэк навигации из `app`, потому что `feature:*` не знают друг о друге.
- Тема только тёмная. Акцентный цвет динамический: вычисляется из обложки играющего трека (MaterialKolor, подгонка тона в HCT под контраст), кэшируется в `album.accent_color`, передаётся в интерфейс через `CompositionLocal` и анимированно меняется при смене трека. В настройках его можно выключить (с 0.5.1), тогда акцент всегда красный. Подробности в `DESIGN.md`, раздел 4, и `docs/decisions/010-accent-extraction.md`.
- Устройство акцента: выбор цвета это чистая функция над пикселями (`IntArray`) в `core:library`, покрытая юнит-тестами без Android. Доступ через интерфейс `AccentRepository` в `core:model`, реализация в `core:library` читает и пишет кэш альбома вне главного потока; цвет трека без альбома хранится только в памяти. `app` следит за текущим треком `PlayerController`, анимирует цвет и передаёт его в `MuzzzloTheme`. `LibraryIndexer` сбрасывает `accent_color` альбома, когда перечитывает изменённый файл.

### Редактор тегов (`feature:tag-editor`)

- Точка входа: пункт Edit tags меню трека в списках, плеере, мини-плеере и очереди. `app` открывает маршрут `tagEditor/{trackId}`.
- Данные идут через `TrackTagRepository` (`core:model`, реализация `DefaultTrackTagRepository` в `core:library`): теги и обложка читаются из самого файла, а не из кэша БД. Запись идёт через `TagWriter` по `content://` URI с именем файла из MediaStore (`DISPLAY_NAME` в БД не хранится, строка MediaStore запрашивается заново). После `Success` трек перечитывается в БД (`LibraryIndexer.reindex`) без полного сканирования; рейтинг и избранное сохраняются, опустевший альбом удаляется.
- Черновик (`TagDraft`) хранит введённый текст как есть. Проверка: номер, итог и год — целые числа от 1 до 9999; итог без номера считается ошибкой, потому что ID3v2 и MP4 хранят их одним значением `3/10`. `changesOf` сравнивает правку с тегами файла после той же обрезки пробелов, что делает запись, поэтому лишний пробел или пустая строка списка изменением не считаются.
- Перед записью всегда показывается подтверждение со списком изменений «было → станет» (выключатель появится в настройках в 0.5.1). Выход с несохранёнными изменениями спрашивает «Discard changes?».
- Разрешение: `TagWriteResult.NeedsPermission` превращается в запрос `TagWritePermission` (`core:tags`, единственная зависимость фичи от `core:tags`), экран показывает системный диалог или запрос `WRITE_EXTERNAL_STORAGE`, после согласия запись повторяется один раз. Повторный отказ показывается сообщением.
- Обложка: выбор через системный photo picker. JPEG или PNG до 1200 px и 1 МБ встраивается как есть, остальное уменьшается до 1200 px по большей стороне и сохраняется в JPEG (качество 90).
- Каждый `TagWriteResult` показывается понятным сообщением; черновик при ошибке остаётся.

### Настройки (`feature:settings`)

- Хранятся в DataStore (Preferences), не в БД, и попадают в резервную копию (раздел 8). Доступ через интерфейс репозитория настроек из `core:model`: модули читают нужные значения как `Flow`, ViewModel экрана настроек их меняет. Значения по умолчанию заданы в одном месте, рядом с репозиторием.

## 10. Тестирование

- Юнит-тесты для `core:model`, разбиения исполнителей, нормализации имён, статистики и миграций.
