# ARCHITECTURE

Описание устройства проекта для разработчиков и для Claude Code.

## 1. Общая схема

```
                     app
                      |
        +-------------+--------------+
        |             |              |
    feature:*     core:designsystem  (DI-сборка)
        |
  +-----+--------+----------+---------+
  |              |          |         |
core:playback  core:library core:stats core:tags
  |              |          |         |
  +--------------+----+-----+---------+
                      |
                core:database
                      |
                 core:model
```

Правила зависимостей:
- `core:model` ни от чего не зависит, это чистый Kotlin.
- `core:database` зависит только от `core:model`.
- Остальные `core:*` зависят от `core:model` и `core:database`, но не друг от друга, кроме явно разрешённых связей: `core:library` использует интерфейс чтения тегов из `core:tags`, `core:stats` слушает события из `core:playback` через интерфейс.
- `feature:*` зависят от `core:*` и `core:designsystem`, но не друг от друга. Навигация между ними собирается в `app`.
- Интерфейсы объявляются в потребляющем модуле или в `core:model`, реализации внедряются через Hilt.

## 2. Данные и источники правды

| Что | Где хранится | Можно пересобрать? |
|---|---|---|
| Теги трека (название, исполнители, альбом, обложка, текст) | Файлы на устройстве | Это и есть источник |
| Кэш для поиска, сортировки, списков | БД (таблицы track, album, artist и связи) | Да, сканированием |
| Алиасы исполнителей, составные имена, оценки, избранное | БД | Нет, попадают в резервную копию |
| События прослушивания | БД | Нет, попадают в резервную копию |
| Настройки интерфейса и воспроизведения | DataStore | Нет, попадают в резервную копию |
| Уменьшенные обложки | Каталог кэша приложения | Да, из файлов |

Подробная схема БД в `DATABASE.md`.

## 3. Сканирование библиотеки (`core:library`)

1. Приложение запрашивает разрешение на чтение аудио (`READ_MEDIA_AUDIO` на Android 13+, `READ_EXTERNAL_STORAGE` ниже).
2. Запрос в MediaStore получает список аудиофайлов с `date_modified` и размером. Подкасты и аудиокниги в библиотеку не попадают (флаги MediaStore, расширение `.m4b`).
3. Файлы, которых нет в БД или у которых изменился `date_modified`, ставятся в очередь на чтение тегов (`core:tags`). Остальные пропускаются.
4. Имена исполнителей проходят конвейер из раздела 4 и превращаются в сущности `Artist`.
5. Результат записывается в БД транзакциями пачками, UI получает обновления через Flow.
6. Файлы, пропавшие из MediaStore, помечаются удалёнными, история прослушиваний сохраняется.

Во время сканирования в памяти держатся `HashMap<нормализованное имя, artistId>` для исполнителей и такая же карта для алиасов. После завершения сканирования карты освобождаются.

## 4. Разбиение исполнителей (`core:tags`)

Правило намеренно простое.

Вход: значения поля «Исполнитель» из файла (одно или несколько).

1. **Несколько значений в файле** (Vorbis/FLAC, ID3v2.4): берём как есть, без дальнейшего разбиения. Значение «Tyler, The Creator» там остаётся одним именем.
2. **Одна строка с `;`**: режем только по `;`. Запятые внутри частей не трогаем, поэтому `Tyler, The Creator; Kanye West` разбирается правильно без всяких правил.
3. **Одна строка без `;`**: режем по `,`, затем среди получившихся фрагментов ищем подряд идущие, совпадающие с записью таблицы составных имён (`artist_compound`, сравнение по нормализованным значениям, сначала самые длинные), и склеиваем их обратно в одно имя. Пример: `Tyler, The Creator, Kanye West` даёт `Tyler, The Creator` и `Kanye West`.
4. **Другие разделители не используются** (`&`, `/`, `feat.`, `and`, `x`): имена вроде «Simon & Garfunkel» и «AC/DC» остаются целыми. Если такое имя нужно разделить, это делается вручную в редакторе тега.
5. **Нормализация и алиасы**: ключ имени (без регистра, лишних пробелов) сначала проходит через таблицу алиасов, затем находится или создаётся исполнитель.
6. **Результат** пишется в `track_artist` с `position`. Исходные значения тега хранятся в `track.artist_tag_values`, чтобы пересчитывать разбиение без чтения файлов.

### Составные имена (запятая внутри псевдонима)

Это единственное исключение из правила запятой. Хранится в таблице `artist_compound` (см. `DATABASE.md`).

- **Встроенный список** лежит в репозитории файлом `core/tags/src/main/assets/compound_artists.json` (поля: `version`, список записей с `id` и `name`). Допускаются дополнения через pull request. При запуске, если версия списка выше сохранённой, недостающие записи добавляются в БД по `builtin_id`. Существующие строки не перезаписываются, поэтому выбор пользователя сохраняется.
- **Добавление пользователем** («Remember as one artist»): в списке исполнителей включается режим множественного выбора, пользователь отмечает несколько записей (например, «Tyler» и «The Creator») и нажимает кнопку. Приложение показывает диалог, где пользователь задаёт порядок и написание («Tyler, The Creator»). Диалог проверяет, что имя состоит из выбранных частей. Правило сохраняется как пользовательское (`builtin_id` пусто).
- **Ручное удаление**: пользовательское правило удаляется совсем, встроенное отключается (`enabled = 0`), чтобы после обновления приложения оно не вернулось.
- **После добавления, удаления или отключения правила** пересчитываются только затронутые треки (по `artist_tag_values`, без чтения файлов), затем удаляются осиротевшие исполнители, у которых нет треков, фото и алиасов. Перед удалением правила показывается предупреждение, что исполнитель снова разделится.
- Файлы на устройстве при этом не меняются. Правила живут в БД и попадают в резервную копию (только пользовательские и отключённые встроенные).

## 5. Запись тегов (`core:tags`)

Самое хрупкое место проекта. Библиотека тегов: TagLib через JNI (`docs/decisions/005-tag-library.md`). Алгоритм:

1. Запросить у системы разрешение на изменение файла: на Android 11+ через `MediaStore.createWriteRequest`, на Android 10 через `RecoverableSecurityException`, на Android 8-9 нужно разрешение `WRITE_EXTERNAL_STORAGE`.
2. Проверить свободное место в личной папке приложения: нужно около двух размеров файла (рабочая копия и резервная копия).
3. Скопировать исходный файл в рабочую копию в личной папке приложения.
4. Записать теги в рабочую копию. Сначала читается полный набор тегов из файла (`PropertyMap`), в нём меняются только наши поля, и записывается он целиком: так сохраняются неизвестные кадры и поля (`TXXX`, `PRIV`, свои поля Vorbis и т.п.). Для MP3 сохраняется исходная версия ID3 (v2.3 остаётся v2.3, v2.4 остаётся v2.4), её нужно передавать при сохранении явно.
5. Прочитать рабочую копию заново и сверить записанные значения с ожидаемыми. Проверить, что аудиоданные не изменились:
   - MP3 и FLAC: хеш байтов аудио после блока тегов;
   - M4A: хеш содержимого `mdat`;
   - OGG и Opus: сравнение аудиопакетов, а не байтов файла, потому что TagLib может перекладывать страницы;
   - для всех форматов: длительность и частота дискретизации по TagLib совпадают с исходными.
6. Создать резервную копию оригинала в личной папке приложения и записать в журнал, что началась замена.
7. Заменить оригинал: записать содержимое проверенной рабочей копии через дескриптор файла (`openFileDescriptor(uri, "rwt")`). Переименовать копию поверх оригинала под scoped storage нельзя, поэтому замена не атомарна.
8. Перечитать оригинал и сверить с рабочей копией (размер и хеш). Только после этого удалить резервную копию и запись в журнале.
9. При любой ошибке до шага 7 оригинал не тронут. При ошибке на шагах 7-8 оригинал восстанавливается из резервной копии. В обоих случаях пользователю показывается понятное сообщение.
10. При запуске приложения проверяется журнал: если замена не была завершена (процесс убит, телефон выключился), оригинал восстанавливается из резервной копии.

Несколько исполнителей пишутся штатно как отдельные значения для Vorbis/FLAC и ID3v2.4. Для ID3v2.3 используется одна строка с разделителем `; ` (то же правило читается при разборе).

### Чтение и JNI

- Перед нативным чтением файл помечается меткой «в обработке», после успешного чтения метка снимается. Если процесс упал в нативном коде, при следующем запуске файл с меткой пропускается и помечается в БД как повреждённый, сканирование продолжается со следующего.
- Строки между Kotlin и C++ передаются как байты UTF-8 в обе стороны (не через `NewStringUTF`, который ломает символы вне BMP). Тест на эмодзи в тегах обязателен.
- Замер скорости чтения на реальном телефоне с большой библиотекой является условием закрытия задачи на чтение тегов.
- Каждый нативный вызов с пользовательским файлом оборачивается в `NativeCallGuard.runGuarded` (`core:tags`): метка лежит файлом в личной папке, по одному на вызов. При запуске `recoverAfterCrash()` переносит оставшиеся метки в карантин, `isQuarantined()` пропускает такие файлы. При параллельном чтении в карантин попадают все файлы, читавшиеся в момент падения. Флаг «повреждён» в БД и связка со сканером появятся в задаче 0.3.2.
- Чтение по дескриптору идёт через `dup()`: дескриптор вызывающего остаётся открытым, но смещение в файле у копии общее и сдвигается.

### Сборка нативной части

- Исходники TagLib подключены git submodule `core/tags/src/main/cpp/taglib`, закреплены на теге `v2.3.2` (вместе с вложенным utfcpp). После клонирования: `git submodule update --init --recursive`. Обновление версии: checkout нового тега в submodule, коммит gitlink, проверка тестов `core:tags`.
- Версии NDK и CMake зафиксированы в `gradle/libs.versions.toml` (`ndk`, `cmake`) и продублированы в `.github/workflows/ci.yml`. Оба пакета ставятся через `sdkmanager`.
- Android: `externalNativeBuild` собирает `libtaglib_jni.so` для arm64-v8a, armeabi-v7a, x86_64 (`c++_static`, в release `MinSizeRel`).
- JVM-тесты: задача `buildHostTagLib` собирает тот же CMake-проект под хост CMake'ом из SDK и системным компилятором C++ (Xcode Command Line Tools или gcc/clang), `jni.h` берётся из JDK, на котором запущен Gradle. Если линкер Command Line Tools старее новейшего macOS SDK (ошибка `tapi error: unknown architecture`), в `local.properties` указывается подходящий SDK: `tags.host.osxSysroot=/Library/Developer/CommandLineTools/SDKs/MacOSX26.5.sdk`, либо обновляются Command Line Tools.
- Лицензии: TagLib используется под LGPL-2.1, utfcpp под Boost 1.0 (`docs/decisions/005-tag-library.md`); тексты лицензий лежат в submodule и попадут в экран лицензий приложения.

## 6. Воспроизведение (`core:playback`)

- `MediaSessionService` на Media3 владеет плеером, очередью и `MediaSession`. Приложение подключается к нему через `MediaController`.
- Уведомление, управление с экрана блокировки и кнопками наушников приходят из Media3.
- Очередь и позиция сохраняются в БД или DataStore при изменениях и восстанавливаются при запуске.
- Аудиофокус и отключение наушников обрабатываются штатными механизмами Media3.
- Gapless, ReplayGain и crossfade добавляются в версии 0.5 поверх этого же слоя без смены архитектуры. Их параметры читаются из репозитория настроек (раздел 9) и применяются к плееру в сервисе, а не в UI.

## 7. Статистика (`core:stats`)

- Слушатель плеера пишет `listen_event` при завершении трека или пропуске. Хранится время начала, фактически проигранное время, длительность трека и снимок названия и исполнителей.
- Прослушивание засчитывается, если проиграно не меньше порога (по умолчанию 50% или 4 минуты, настраивается). Пропуски помечаются отдельно.
- Агрегации (топы, карты активности, серии дней) считаются SQL-запросами и Flow, без хранения готовых итогов.
- Исполнители считаются по отдельности через `track_artist`, поэтому "A & B" не появляется отдельной строкой.
- Экспорт и импорт: JSON (полный) и CSV (события). Формат версионируется полем `schemaVersion`.

## 8. Резервная копия

Один файл JSON: алиасы, пользовательские составные имена и отключённые встроенные, события прослушивания, оценки, избранное, настройки. Теги в копию не входят, они находятся в файлах. Импорт проверяет `schemaVersion` и объединяет данные без дублей.

## 9. Интерфейс

- Один `Activity`, навигация Compose Navigation, состояние экранов в ViewModel (`StateFlow`).
- Дизайн-система в `core:designsystem` (цвета, типографика, базовые компоненты), значения берутся из макета Figma.
- Тема только тёмная. Акцентный цвет динамический: вычисляется из обложки играющего трека (Palette или Material Color Utilities, подгонка тона под контраст), кэшируется в `album.accent_color`, передаётся в интерфейс через `CompositionLocal` и анимированно меняется при смене трека. В настройках его можно выключить, тогда акцент всегда красный. Подробности в `DESIGN.md`.

### Настройки (`feature:settings`)

- Хранятся в DataStore (Preferences), не в БД, и попадают в резервную копию (раздел 8). Доступ через интерфейс репозитория настроек из `core:model`: модули читают нужные значения как `Flow`, ViewModel экрана настроек их меняет. Значения по умолчанию заданы в одном месте, рядом с репозиторием.
- Каркас экрана и первые пункты появляются в задаче 0.5.1, остальные пункты добавляет задача, которая реализует соответствующую функцию (`ROADMAP.md`).
- Решение о составе и порядке появления: `docs/decisions/009-settings.md`.

## 10. Тестирование

- Юнит-тесты для `core:model`, разбиения исполнителей, нормализации имён, статистики и миграций.
- Тесты Room на эмуляторе или Robolectric, миграции проверяются через `MigrationTestHelper`.
- Набор эталонных аудиофайлов для тестов тегов (маленькие, собственного производства).
- Ручная проверка на реальном устройстве обязательна для фонового воспроизведения.
